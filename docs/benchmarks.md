# FlashSpec Benchmarks

## The 0.3.0 release measurement

Run from `main` at git `3c43e08` with `benchmarks/configs/qwen_t4_release_030.yaml`
(notebook cell 3g): the 0.2.0 release config plus `drafter_strategy: auto`,
which resolved to `composite-g6-f2` in every FlashSpec result. Same pair,
prompts, modes and methods as 0.2.0, one Tesla T4, one session. The README
tables are generated from this bundle only
(`scripts/ingest_gpu_bundle.py --readme-commit 3c43e08`); the JSONs are in
`benchmarks/results/gpu/3c43e08/`.

- Compiled FlashSpec was faster than compiled HuggingFace in all four cells,
  by at least 1.5x on HumanEval and by less on MT-Bench.
- The eager path (`compile=False`) was faster than plain HuggingFace
  `generate` in all four cells and slower than compiled HuggingFace in all
  four.
- Greedy output matched compiled HuggingFace on 9/10 HumanEval and 8/10
  MT-Bench prompts. On all 20 prompts both sides' outputs are identical,
  token for token, to the tie-checked comparison run (bundle `fdd3be9`), so
  the three divergences are the fp16 exact ties found there and in #47.
- The first compiled call (compile and CUDA-graph capture) is recorded in the
  README's cold-start line; warmup prompts keep it out of the tables.

## The 0.2.0 measurement and its scope

Moved from the README (0.3.0 README restructure). The README tables showed
this run until 0.3.0; they now show the 0.3.0 release run above.

**Project status at 0.2.0: alpha, version 0.2.0.**

**What was measured, and only this:** one model pair
(`Qwen/Qwen2.5-1.5B-Instruct` verified by `Qwen/Qwen2.5-0.5B-Instruct`),
one Tesla T4, fp16, batch 1, 10 MT-Bench and 10 HumanEval prompts, run
from `main` at git `8d036d7` with the default `FlashSpecConfig(compile="auto")`,
which turned the compiled path (static KV cache and CUDA graphs) on. On
that setup FlashSpec was faster than HuggingFace `generate` compiled the
same way in every cell of the table below: by at least 1.3x on both
HumanEval cells, and by less on MT-Bench. With the eager path
(`compile=False`) it was slower than plain HuggingFace `generate` in 3 of
the 4 cells of the same run (generated table in the README). No other GPU,
model pair or batch size has been measured. Every H100 number in the docs
is a design target.

- **The first call compiles.** On CUDA with Triton, the default
  `compile="auto"` compiles the drafter and target forwards and captures
  CUDA graphs on the first `generate`, which can take minutes. Later calls
  reuse them. The README tables exclude that first call (warmup
  prompts absorb it). To skip compilation, pass
  `FlashSpecConfig(compile=False)` (the eager path, slower here) or
  `--compile off` to the server. The engine logs one line saying whether
  the compiled path is on and why.

- **Correctness** is checked in CI on CPU: a chi-squared test that emitted
  tokens follow the target when draft and target differ, and a
  token-for-token comparison of greedy output with
  `generate(do_sample=False)`. On the GPU in fp16, kernels for different
  shapes can round differently, so each greedy GPU run reports how many
  prompts matched (last columns of the README table).
- **The bandit is experimental.** Until Phase 6 every measured run used one
  drafter. The Phase 6 run (bundle `3e38251`) measured it choosing among
  seven arms, and it did not beat the best fixed arm on the mixed workload.
- **The Triton and assembly kernels are experimental** and not on the
  generation critical path; see [Kernels: measurements](kernels.md#measurements-moved-from-the-readme).
- `sampling.variant="typical"` is **lossy**; `"rejection"` and `"greedy"`
  are the lossless variants.

This is a single-device library plus a small HTTP server, not a
production serving stack.

## Methodology

Committed result JSON follows the schema described in
`benchmarks/README.md`. `benchmarks/results/baseline.json` is a template,
not a measurement. Once a result JSON is committed, the config that
produced it stays as it was committed.

### Hardware the paper configs were written for

These rows describe the machine the Llama configs target. They are not
a record of a run. This checkout has no committed H100 result. A config
whose device is missing, or whose checkpoint cannot be loaded, writes
no JSON.

| Field        | Intended paper machine |
|--------------|------------------------|
| GPU          | NVIDIA H100 SXM5       |
| CUDA         | 12.4                   |
| Driver       | 550.x                  |
| Precision    | bfloat16               |
| Batch size   | 1                      |

### Warmup

The Llama configs under `benchmarks/configs/` set 50 warmup steps. The
committed CPU HumanEval/23 pair at git `f59b5b4` is recorded in
`benchmarks/results/README.md` with `n_warmup` 0. That field is not in
the result JSON itself. Cite the notes for the run you quote.

### Datasets

- **MT-Bench**: conversational multi-turn benchmark. No MT-Bench generation
  result is committed.
- **HumanEval**: Python code generation. The committed CPU pair uses
  HumanEval/23.
- **Alpaca**: named as an instruction-following set. The Alpaca text is
  not in this tree, and no Alpaca generation result is committed.
- **HumanEval-edit** (`humaneval_edit`): 10 copy-heavy code-editing prompts
  built from HumanEval (MIT), for the prompt-lookup drafter. See
  `benchmarks/prompt_sets/README.md` for the selection rule and license.
- **Mixed** (`mixed`): the 30 MT-Bench, HumanEval and HumanEval-edit prompts
  in one stored shuffled order, run on one engine so a bandit's state
  carries across prompts.

### Phase 6: bandit against fixed arms

`benchmarks/configs/qwen_t4_phase6.yaml` (`runner: phase6`, run by
`benchmarks/phase6.py`) measures every fixed arm, {Qwen2.5-0.5B, n-gram} x
gamma {2, 4, 6} plus the composite arm, against the UCB1 and Thompson
bandits over all of them, on each set and on the mixed workload, next to
compiled HuggingFace. `scripts/phase6_report.py <results dir>` prints the
exit criteria from the JSONs. Result (bundle `3e38251`, in
`benchmarks/results/gpu/3e38251/`): the bandit failed its main exit
criterion; see the CHANGELOG.

### Default drafter strategy: composite-g4 against composite-g6-f2

`benchmarks/configs/qwen_t4_composite.yaml` (same runner, models, prompts,
modes and seed as Phase 6; notebook cell 3f) runs the two composite
variants alone, next to compiled HuggingFace (and eager HuggingFace greedy
as context), on each set and on the mixed workload. With
`greedy_tie_check: true`, every greedy output that differs from
`hf_greedy_compiled` is replayed after its block and classified by
`benchmarks/tie_check.py`: an allowed fp16 exact tie (same prefix, the two
diverging tokens are both rows' top 2, one row's top-2 margin is exactly
0.0, both replays reproduce the recorded outputs) or a mismatch.

The decision rule is fixed in the config before the run, and
`scripts/composite_report.py <results dir>` applies it: the variant with
the higher mixed greedy throughput is picked; it becomes the default only
if it beats compiled HuggingFace on every single set in both modes and its
greedy output matches compiled HuggingFace except at allowed exact ties.
Otherwise neither variant becomes the default from this run.

Result (bundle `fdd3be9`, Tesla T4, one session; JSONs in
`benchmarks/results/gpu/fdd3be9/`): the rule passed for the pick. composite-g6-f2 had the higher mixed-workload greedy throughput, was faster than compiled HuggingFace on HumanEval, MT-Bench and HumanEval-edit in greedy and at T=0.7, and matched compiled HuggingFace greedy output except at three fp16 exact ties (HumanEval/53, MT-Bench 81 and 101, the ties the #47 diagnostic found). composite-g4 also passed both checks, with no greedy divergence.
`composite-g6-f2` is therefore what `drafter_strategy="auto"`, the default,
runs with one model drafter at batch 1.

### 0.3.0 release measurement

`benchmarks/configs/qwen_t4_release_030.yaml` (notebook cell 3g, run from a
commit on `main`) is the 0.2.0 release config with one added key,
`drafter_strategy: auto`, so both FlashSpec methods run the way a default
0.3.0 user gets them. The harness key `drafter_strategy` defaults to
`bandit`, the model-drafter path every earlier config measured. Each
FlashSpec document then records the requested and resolved strategy and a
per-arm report. The compiled method's drafter forwards are derived from the
per-step arm records, because lookup steps run no drafter. The README
tables for 0.3.0 are generated from that bundle only.

## Running benchmarks

```bash
# Fast smoke-test (no GPU or weights required). Writes no quoted result.
make bench-quick

# This machine's CPU measurements: residual, synthetic bandit, toy model.
make bench-cpu

# Full benchmark (requires GPU + model weights):
make bench
```

`make bench` and `make bench-cpu` write JSON under `benchmarks/results/`.
CPU result files live under `benchmarks/results/`. The root README
does not name the host machine. `make bench-quick` is a smoke test.

`notebooks/04_gpu_measurement.ipynb` is the GPU measurement. The Colab
Tesla T4 run at git `cb02ca1` is in
`benchmarks/results/tinyllama_gpu_flashspec_ucb_cb02ca1.json` and
`benchmarks/results/tinyllama_gpu_vanilla_ar_cb02ca1.json`. A later GPU
run still has to be downloaded from Colab and copied here. Google Drive
is not this repository. A CPU float32 HumanEval/23 pair at git `f59b5b4`
is in `benchmarks/results/tinyllama_cpu_humaneval_flashspec_ucb_f59b5b4.json`
and `benchmarks/results/tinyllama_cpu_humaneval_vanilla_ar_f59b5b4.json`.

## Adding a new benchmark

1. Create a YAML config in `benchmarks/configs/`.
2. Do not modify existing configs after first commit.
3. GPU configs run on a Colab T4 through `notebooks/04_gpu_measurement.ipynb`
   (there is no GPU CI runner); ingest the bundle with
   `scripts/ingest_gpu_bundle.py`.
